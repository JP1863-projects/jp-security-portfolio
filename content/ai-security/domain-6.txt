@6.1|Threat modeling and adversarial behavior
An architecture review lists generic threats without identifying assets or actors. What should be established first?|System scope, assets, trust boundaries, and credible adversaries|The final severity score|The model's preferred response format|The largest possible test corpus|Threat modeling needs a defined system and context before useful attack paths or priorities can be assessed.
A public document tells a RAG assistant to ignore its instructions. Which threat is most directly involved?|Indirect prompt injection through retrieved content|Training-time label poisoning|Model weight extraction|Membership inference|The attacker supplies instructions through material the assistant retrieves rather than directly through the legitimate user's request.
An attacker changes a test-time image to fool a deployed classifier. How does this differ from poisoning?|It targets inference input rather than the training process|It requires changing training labels|It proves the model was copied|It only affects dataset licensing|Evasion changes inputs to an existing model; poisoning manipulates learning data or training behavior.
An internal engineer can alter a model release manifest. What should threat modeling include?|Insider or compromised-maintainer artifact substitution|Anonymous public prompt attacks|Physical theft of user devices|Unrelated phishing against customers|Threat models should include privileged insiders and compromised internal identities, not just external users.
An agent stores instructions from an untrusted page in persistent memory. What attack path should be modeled?|Delayed influence across future sessions|A single transient response|Accelerator overheating|Software license expiration|Persistent state can carry attacker influence beyond the original retrieval and affect later decisions.
A multi-agent workflow lets one agent claim another has approved an action. What is the security concern?|Unverified delegation and fabricated approval authority|The message's spelling|Model throughput|A lack of shared embeddings|Approval claims need verifiable provenance and scope; peer-generated assertions cannot create trusted authorization.
A malicious input causes extremely long model reasoning and expensive tool loops. What consequence should be assessed?|Resource exhaustion and denial of service|Training-data membership leakage|Copyright infringement|Signature verification failure|Expensive inference and repeated tool actions can degrade availability and create financial or operational impact.
A threat model ends at the model's text output although tools execute it. What is missing?|Downstream action paths and their authorization boundaries|The model's release year|The interface's color palette|Training hardware details|Consequences often occur after generation; include the services and resources affected by model-driven operations.
An attacker combines text in an image with an audio instruction. What should the model's threat coverage include?|Cross-modal input interpretation and resulting action paths|Typed chat messages|Image file extensions|The provider's clean benchmark|Multiple modalities can convey attacker-controlled content; assess their combined effects in the actual workflow.
A detector's target is stable, but attackers adapt their samples to avoid it. What should threat analysis consider?|Adaptive adversaries and changing attack distributions|Random benign traffic|Data-center power consumption|The model card's publication date|Security evaluations should account for actors actively adjusting inputs in response to deployed defenses.
An organization maps AI attacks only to a traditional network checklist. What should be added?|AI-specific data, model, retrieval, and agent attack techniques|Additional firewall brand names|Standard uptime checks|User satisfaction surveys|Traditional methods remain useful but need expansion to represent distinctive AI components and failure paths.
An attacker wants to learn sensitive attributes rather than steal weights. Which distinction matters?|The target is private information, not necessarily model ownership|Every attack must extract model weights|All privacy attacks require physical access|A copied model is the only possible outcome|Threat objectives differ; inversion and inference can harm privacy without copying the model artifact.
@6.2|Secure lifecycle and change
A model release passes tests, but the application changes its tool permissions afterward. What should be reevaluated?|The changed system's action exposure and controls|Model weights|The original benchmark|The release certificate|Security assurance applies to a configuration and use case; changed authority can invalidate earlier conclusions.
A team changes the embedding model but keeps the old vector index. What should be verified?|Compatibility and retrieval quality before promotion|The model file size|User authentication|Database uptime|Embedding changes may invalidate similarity behavior or require reindexing; test the integrated retrieval path.
A dataset update is treated as content maintenance outside change control. What should policy recognize?|Data changes can materially alter AI behavior and risk|Executable code can affect behavior|Dataset changes need no owners|A signed deployment always covers future data|Models and retrieval systems depend on data; lifecycle controls should cover consequential content changes.
A new model is canaried without monitoring security-specific outcomes. What should rollout include?|Relevant policy failures, action anomalies, and rollback criteria|Average response speed|Total request counts|The model version banner|Staging limits exposure only when the team can detect the failures that should halt expansion.
A deployment rollback reverts the application but leaves an overprivileged agent role. What remains unresolved?|The changed authorization state|The source code version|Model weights|The old chat transcripts|Rollback must include security-relevant configuration and entitlements, not just application binaries.
A team uses a development prompt containing test bypass instructions in production. What control should prevent this?|Environment separation and validated configuration promotion|Stronger production hardware|Lower output limits|A new model provider|Development settings can weaken production behavior; configuration belongs in controlled release checks.
A model update changes previously stable refusal behavior. What should release review assess?|Security regressions and approved use-case behavior|Improved general benchmarks|Token pricing|Faster startup|General gains can coexist with weakened controls; test relevant behavioral boundaries after changes.
A release record tracks the model but not its system prompt. What should be versioned?|Prompts, tool definitions, retrieval, and other behavior-relevant configuration|Model parameter counts|The developer's username|The release meeting notes|System behavior depends on more than weights; reproducibility and review require the relevant combined configuration.
A pipeline runs regression tests using live customer identities with write permissions. What should be improved?|Isolated tests with synthetic data and bounded test authority|A warning to testers|Faster cleanup after tests|A shorter test name|Testing should avoid unnecessary production exposure and unintended consequential actions.
A team wants to accelerate emergency model updates. What should remain in the process?|Defined emergency authority, essential validation, evidence, and follow-up|Automatic unreviewed permanent access|No recording of changes|A blanket exemption for every update|Emergency procedures can be faster while retaining accountability and minimum controls appropriate to urgency.
An integration is approved for one model version but silently switches providers. What should change management require?|Reassessment of the new provider, data flow, behavior, and dependencies|A new brand label|Confirmation the API syntax matches|Matching response length|Compatible interfaces do not imply equivalent handling, security, or behavior across providers.
A security gate is skipped for minor releases without defining minor. What should be clarified?|Risk-based change criteria and required validation for each category|A fixed naming convention|The release date format|Who writes release notes|Ambiguous exemptions can hide consequential changes; define criteria tied to actual exposure and behavior.
@6.3|Procurement and provenance
A supplier's model digest matches, but the download channel's owner is unknown. What still needs verification?|Trusted origin and authorization of the reference|A second hash of the same file|The file's timestamp|The filename suffix|Matching bytes to an untrusted reference does not establish the artifact's legitimate origin.
A model package bundles a third-party component omitted from its inventory. What should procurement request?|An accurate dependency record and assessment of the added component|A corrected logo|More inference credits|The model's training duration|Undisclosed components can introduce vulnerabilities, rights issues, and unexpected data flows.
A vendor permits inference but prohibits redistribution of weights. What should the deployment team check?|Whether packaging and distribution plans comply with the license|Whether the artifact is encrypted|Whether the application is private|Whether the file can be downloaded|Technical ability and access restrictions do not automatically authorize redistribution.
A provider changes its subcontracted inference platform. What should supplier management assess?|Changed recipients, controls, locations, and contractual responsibilities|Whether the API hostname stays the same|Response grammar|The monthly invoice number|Hidden infrastructure changes can affect privacy, continuity, and security even behind an unchanged interface.
A team signs its own copy of an unreviewed external model. What does that signature establish?|Its endorsement or packaging step, not original safety or provenance|That all original risks are removed|That the original vendor authorized every use|That training data was independently audited|Signing a copy records a trust action; it does not retroactively validate unknown source material.
An acquisition checklist asks only whether the model has a security certificate. What else is needed?|Use-specific evidence, provenance, data handling, and operational fit|A larger certificate image|A list of competitors|A positive sales reference|Procurement must evaluate the actual service and intended use rather than rely on broad assurance labels alone.
A supplier discloses a training-data incident affecting some versions. What record helps establish exposure?|Exact model and dataset dependency versions tied to releases|The supplier name|The current marketing page|Total yearly usage|Granular dependency records determine which deployed artifacts inherit the affected supply-chain component.
An imported model claims to be a trusted release but has a different signer. What should happen?|Investigate the trust-chain discrepancy before approval|Accept it because the name matches|Ignore signer changes when the model is smaller|Treat local storage as independent validation|Unexpected signing identity changes can indicate substitution; verify through an established trusted channel.
A vendor assessment is reused for a product that now trains on customer prompts. What is required?|Review the changed data use and update the approval decision|Verify the invoice is current|Confirm the same vendor owns it|Increase prompt limits|Supplier approval depends on actual handling; a material new purpose changes the risk assessment.
A supplier cannot provide evidence needed for a mandatory requirement. What should the buyer do?|Resolve the gap, seek an approved alternative, or reject the use|Assume missing evidence means compliance|Rely on model confidence|Mark the requirement passed for schedule reasons|Unverified mandatory requirements should remain explicit decision gaps rather than being silently treated as satisfied.
An AI bill of materials is complete but never updated. What is the concern?|The inventory no longer reflects deployed dependencies|Its original accuracy guarantees future accuracy|Version changes cannot affect security|The model cannot be used offline|A component inventory supports assurance only while it tracks actual deployed versions and relationships.
@6.4|Testing and red teaming
A red-team plan says break the chatbot without defining success. What should be specified?|Scope, allowed actions, expected boundaries, evidence, and stop conditions|The number of testers|The preferred model|A catchy exercise name|A useful assessment needs authorized boundaries and observable criteria distinguishing failures from harmless oddities.
A tester discovers a real secret during an approved exercise. What should they do?|Follow the agreed handling and escalation process and limit exposure|Publish it to prove the finding|Use it against unrelated systems|Store it in a public prompt library|Authorization to test does not grant unrestricted handling or reuse of sensitive material discovered during testing.
A prompt-injection test only asks the model directly to ignore instructions. What broader path should be tested?|Indirect instructions in retrieved documents and tool results|More polite direct requests|Larger batch sizes|Model startup checks|A system may resist direct attacks yet fail when hostile instructions arrive through trusted-looking context channels.
A test validates that a tool denies unauthorized actions. What should also be examined?|Alternate tools, retries, parameter changes, and delegated paths|The denial message's punctuation|The model's greeting|Query response speed|Equivalent paths can bypass a single successful check; test the underlying boundary across realistic routes.
A red team reports only one successful jailbreak from thousands of trials. What should reporting include?|Test conditions, trial counts, success frequency, and impact|The most dramatic screenshot|The model brand|A binary claim that AI is unsafe|Frequency and conditions help interpret reliability and operational significance alongside demonstrated impact.
A security test intentionally sends unlimited expensive requests to production. What should authorization and design address?|Availability limits, cost bounds, stop conditions, and safe environment choice|How to maximize token use|Whether requests use valid syntax|Tester convenience|Authorized testing still needs bounded impact, particularly for resource-exhaustion and costly-action scenarios.
A test uses a document an employee is legitimately allowed to read and calls any citation a leak. What should be clarified?|The intended authorization boundary and expected result|Whether the citation is long|The embedding model version|Whether the text is technical|A disclosure finding needs an unauthorized recipient, prohibited purpose, or other violated requirement; access context matters.
A model passes tests in English. What should multilingual deployment testing include?|Supported languages and relevant cross-language attack cases|English with different fonts|Provider summary benchmarks|Translated interface labels|Safety and authorization behavior can vary with language; evaluate the actual supported inputs and outputs.
A tester copies an exploit prompt without recording system configuration. What is missing?|Reproducible context including versions, settings, tools, and relevant data|A more memorable prompt title|A response timestamp|A model parameter estimate|Identical text can behave differently across system states; reproduction needs the conditions enabling the failure.
A red-team tool can modify production permissions but the exercise covers only read-only behavior. What should be done?|Restrict the tool to the authorized scope|Assume unused permissions are harmless|Allow changes if the model asks|Rely solely on tester memory|Test infrastructure should enforce scope and minimize authority rather than depend only on intentions.
A multimodal test suite ignores metadata and extracted text. What should coverage assess?|All input paths that reach model context or tools|The visible pixels|File upload success|Image dimensions|Processing can expose text or metadata to downstream components; assess the actual interpretation path.
@6.5|Assessment and reporting
A generated answer is offensive but cannot trigger actions or access restricted data. What should severity analysis consider?|Actual harm, affected users, context, and available paths|Assign the highest technical severity automatically|Ignore all user impact|Use only response length|Assess consequences in context; harmful content and privilege compromise need evidence appropriate to their distinct impacts.
Two testers reproduce a flaw only under one specific configuration. What should the finding state?|The affected configuration, preconditions, evidence, and limits|That all AI deployments are vulnerable|That only the vendor is responsible|That configuration details are irrelevant|Precise scope supports correct remediation and avoids overstating evidence beyond what was demonstrated.
A report says prompt injection without describing the consequence. What should be added?|The crossed boundary and demonstrated or credible impact|More attack terminology|The exact model size|The tester's preferred tool|A technique label is not sufficient to prioritize; explain what access or action the attack enabled.
An executive asks whether the new fix removes all AI risk. What should the assessor communicate?|Validated improvement, test scope, remaining exposure, and uncertainty|A guarantee of perfect safety|Raw test prompts|The vendor's slogan|Assurance should match observed evidence and acknowledge limits rather than promise untestable completeness.
A finding maps to an industry framework but lacks reproduction evidence. What is still needed?|Evidence of the issue in the assessed system|A second framework label|A more severe category|An expanded acronym|Framework mapping organizes understanding; it does not prove a vulnerability exists in a particular deployment.
A triage team prioritizes an unusual answer over a reproducible unauthorized transfer. What should guide ordering?|Impact, exploitability, exposure, and control effectiveness|Novelty|Social media interest|Answer length|Prioritize consequential security failures using evidence rather than the surprise value of model behavior.
A report includes raw customer records as screenshots. What should the author do?|Minimize or redact sensitive evidence while preserving the proof|Share the full records with every recipient|Assume reports are exempt from privacy controls|Remove all evidence without replacement|Evidence should remain useful and verifiable without unnecessary disclosure to report readers.
A tester demonstrates an attack only after disabling the production authorization gate. What should the finding disclose?|The changed precondition and whether normal deployment is affected|Present the result as a production bypass|Omit the disabled gate|Claim the original control failed|Test modifications materially affect interpretation; findings must distinguish normal exposure from hypothetical weakened configurations.
A remediation owner disputes a severity score. What is the best basis for discussion?|Reproducible impact, exposure, assumptions, and existing controls|The scorer's seniority|The longest report|A vendor's reputation|Severity disagreement should be resolved with evidence and a shared risk method rather than authority or presentation.
A report treats every hallucination as data exfiltration. What distinction should be made?|Fabrication differs from disclosure of actual protected information|All invented data came from training|Every incorrect answer proves compromise|Accurate answers can cause harm|Reliability failures and confidentiality failures can overlap, but classification requires evidence of what actually occurred.
A technical report is sent to leadership without business context. What should be added?|Affected processes, consequences, choices, and accountable next steps|Additional exploit syntax|More model architecture details|A longer appendix|Decision-makers need the implications and available actions, not just mechanics of the technical finding.
@6.6|Mitigation validation
A prompt-only fix stops one known attack string. What should validation assess?|Generalization to related inputs and enforced downstream boundaries|Exact-string rejection|Whether the prompt is longer|Whether the model apologizes|A patch may overfit the demonstrated input; validate the boundary against variants and independent controls.
A team blocks one attacker domain after an unauthorized export. What broader control should be considered?|Destination restrictions and action authorization for data exports|That domain's spelling variants|A more emphatic system prompt|Daily model restarts|Blocking one indicator may leave the underlying export capability exploitable through another destination.
A rate limit reduces extraction speed. What should the risk owner understand?|It may increase attack cost without eliminating extraction risk|It cryptographically prevents all model copying|It validates every dataset license|It removes the need for authentication|Mitigations can reduce feasibility or impact without removing the threat; assess residual exposure explicitly.
A model is adversarially trained on a test set and then evaluated on that same set. What is needed?|Independent held-out evaluation including relevant unseen attacks|A higher score on the reused set|More training epochs|A new name for the set|Reusing training examples for final evaluation can overstate robustness; evaluate generalization independently.
A fix denies all retrieval, eliminating leaks but breaking the approved function. What should be tested?|Both unauthorized denial and authorized successful use|Whether leaks disappear|Frontend availability|The total number of denials|An effective control should meet security requirements while preserving intended permitted behavior where required.
A team chooses a complex control it cannot operate reliably. What should mitigation planning consider?|Operational feasibility, coverage, failure behavior, and ownership|Theoretical sophistication|How many features it offers|The vendor's demo|A control's practical effectiveness depends on being correctly deployed, maintained, observed, and handled when it fails.
A watermark is proposed as the sole defense against confidential output disclosure. What is the limitation?|Attribution markings do not independently prevent disclosure|A watermark automatically enforces access|A watermark revokes leaked credentials|A watermark removes every sensitive fact|Watermarks can support provenance or attribution; prevention requires controls on data access and output paths.
A sandboxed agent can still use an approved tool to disclose restricted records. What should be remediated?|The tool's authorization and data-release policy|The sandbox's filesystem settings|The model's vocabulary|The operating-system wallpaper|Isolation does not replace resource authorization; an allowed interface can still enable excessive access.
A vulnerability is fixed, but monitoring has no signal for recurrence. What should be added?|A relevant regression case and ongoing detection where appropriate|A closed ticket|A new model version number|A renamed alert folder|Verification and monitoring help establish that a fix remains effective as data, tools, and configurations change.
A control reduces false positives by allowing every uncertain output. What should evaluation examine?|Whether harmful false negatives and consequences increase|The improved acceptance rate|Faster response time|Fewer helpdesk complaints|Optimizing one metric can worsen another; evaluate both error types and their operational impact.
A release passes the original exploit test but fails a related delegated-action test. What should the release decision be?|Address the remaining boundary failure before claiming remediation|Declare success based on the original test alone|Exclude the related test silently|Disable the test permanently|Remediation claims should reflect the relevant failure class and unresolved evidence, not one favorable test result.
