@4.1|Architecture and trust boundaries
A RAG application checks permissions only when documents are indexed. What is missing?|Authorization reflecting the requester at retrieval time|A longer indexing interval|Encryption of the search query|A larger vector dimension|Indexing-time permissions can become stale or differ by requester; enforce current access before returning content.
An agent trusts every response from an internal tool as an instruction. What should architecture enforce?|Treat tool content as data and constrain subsequent actions|Give tool output higher authority than application policy|Allow responses to grant credentials|Replace tool authentication with textual assurances|Internal tools can return compromised or attacker-controlled content; content cannot expand action authority.
A private inference endpoint can retrieve arbitrary public URLs. What should be assessed?|Server-side request forgery and outbound access boundaries|Whether the model is local|Whether requests use natural language|Model download licensing|A URL-fetch capability can reach unintended destinations; enforce network and destination controls independently of generated requests.
A company is choosing hosted versus self-managed inference. What is the strongest decision basis?|Data requirements, capabilities, threats, cost, and operational capacity|Assume self-hosting is always safer|Assume hosting removes all customer responsibility|Choose only by parameter count|Deployment choice changes responsibilities and controls; evaluate the complete operating context rather than a universal preference.
A system prompt contains a rule against disclosing secrets that are included in every context. What should change?|Keep unnecessary secrets out of model context|Repeat the rule more often only|Increase answer creativity|Assume the prompt establishes confidentiality|Avoiding exposure is stronger than relying on model obedience after sensitive material is supplied.
A tenant identifier in a query is accepted directly from user text. What should determine tenant scope?|Authenticated application context and enforced policy|Whatever tenant the prompt names|The nearest embedding cluster|The model's inferred employer|Untrusted query content cannot establish tenant authority; derive scope from verified identity and permissions.
A security architect draws only the model and frontend. What should the diagram add?|Data stores, identities, tools, dependencies, and trust boundaries|A larger model icon|Training-loss curves|Token prices|Threat modeling needs the actual paths where data and authority move, including supporting services.
A chat response is inserted into a web page as raw HTML. Which control is most relevant?|Safe rendering and context-appropriate output encoding|Prompt phrasing|Model weight signing|Dataset lineage|Generated text is untrusted output; browser rendering needs controls against executable or unsafe markup.
An assistant can call an arbitrary command interpreter for a narrow reporting task. What architecture is preferable?|A constrained reporting API with validated parameters|A broader shell with a warning prompt|Administrator shell access with logging only|A hidden unrestricted console|A task-specific interface limits available operations and supports enforceable validation and authorization.
A guardrail service fails during a request. For an action that requires its approval, what should happen?|Deny or safely defer the action according to policy|Execute by default to preserve speed|Let the model invent an approval|Skip audit evidence|Required authorization or safety gates should not silently disappear during component failure.
A system optimizes latency by bypassing retrieval permission checks. What should leadership require?|A design meeting both access requirements and acceptable performance|A permanent security exception without review|A statement that faster access is safer|Removal of per-user identities|Performance tradeoffs must not silently invalidate mandatory access boundaries; redesign or explicitly reassess the use case.
@4.2|Infrastructure isolation
Two tenants share inference infrastructure. What should prevent cross-tenant data disclosure?|Enforced isolation across memory, caches, storage, and request context|Distinct chat colors|Separate billing labels|A larger accelerator|Isolation must cover the actual shared resources and execution paths where tenant data can cross boundaries.
A training job runs as a host administrator. What should be reduced?|Execution privilege and host access|The number of labels|The dataset's line length|The model output size|Training code and dependencies should run with least privilege and appropriate isolation to limit compromise impact.
An inference container has unrestricted outbound network access. What should security design consider?|Destination allowlists and necessary egress restrictions|Whether incoming traffic uses TLS|More verbose prompts|Public model ratings|Outbound controls limit exfiltration and unintended service access that inbound encryption does not address.
A long-running request exhausts accelerator memory. Which control is most relevant?|Bound input size, concurrency, and execution resources|Rotate user passwords|Disable access logs|Rename the endpoint|Resource limits must constrain expensive workloads before they destabilize shared infrastructure.
A lab downloads untrusted training packages. Where should initial evaluation occur?|An isolated environment without production credentials|A production deployment host|A shared privileged workstation session|A live data-processing pipeline|Isolation limits the consequences of malicious code or artifacts during evaluation.
A model platform's management interface is publicly reachable with default credentials. What is the priority?|Restrict exposure and replace insecure defaults through approved administration|Compress the model|Document the default password|Increase instance capacity|Exposed administrative access creates a direct compromise path that model-specific controls do not resolve.
A cloud training workload uses a public bucket for temporary sensitive files. What should change?|Protect temporary storage with appropriate access and lifecycle controls|Protect only permanent datasets|Assume temporary files disappear immediately|Shorten filenames|Intermediate artifacts can retain sensitive data; temporary status does not remove confidentiality requirements.
A failover region lacks the required data-handling controls. What should continuity design do?|Validate or redesign failover before approving it|Fail over first and review later|Assume any region is equivalent|Synchronize model weights|Recovery must preserve security and handling requirements, not just restore service availability.
A GPU host is secure logically but exposed to physical tampering. What should be reviewed?|Physical access, environmental protection, and relevant hardware trust|Output filters|Model cards|Prompt length|AI infrastructure still depends on physical and environmental controls in addition to logical isolation.
An inference service runs beside a sensitive management service with broad shared permissions. What should improve?|Workload separation and narrowly scoped trust relationships|A shared service name|Common logging format|Uniform model versions|Unnecessary co-location and shared authority can expand lateral-movement opportunities and compromise impact.
A compute quota is enforced per API key, but users can create unlimited keys. What should limits consider?|Account or tenant-level aggregate usage|Each individual key|Daily average latency|Response text length|Limits can be bypassed through identity multiplication unless the relevant aggregate principal is also constrained.
@4.3|Secure deployment pipelines
A build runner can both train a model and approve its production release. What should be reviewed?|Separation of duties and controlled promotion authority|The runner's hostname|The number of training epochs|Artifact compression|Separating creation from approval reduces the chance that one compromised or mistaken actor bypasses release controls.
A CI pipeline downloads the latest model on every build without pinning it. What should improve?|Verified immutable references and reviewed dependency changes|The deployment schedule|The dashboard layout|The log retention period|Unpinned mutable dependencies can change behavior without an intentional reviewed release.
A serving image is patched, but its training-stage dependencies remain vulnerable. What should be assessed?|Security across the complete build and training pipeline|The runtime image|End-user browser versions|The model's input syntax|Training and build compromise can affect resulting artifacts even when the final serving container is patched.
A release gate checks model accuracy but not the retrieval corpus version. What should be included?|Versioned evaluation of the full deployed system|The weights' parameter count|User satisfaction comments|The CI runner's uptime|Behavior depends on model, data, retrieval, tools, and configuration; validate the integrated release state.
A pipeline accepts unsigned artifacts from an unauthenticated storage path. Which control combination is strongest?|Trusted artifact verification and authenticated controlled retrieval|An obscure URL|A larger download timeout|Filename validation|Both origin and transfer access matter; obscurity and filenames do not establish artifact authenticity.
A fine-tuning run cannot be reproduced because preprocessing settings were lost. What should be retained?|Versioned transformation configuration and dataset references|The final model nickname|The GPU's purchase date|A screenshot of training progress|Reproducibility requires the inputs and transformations that determine the trained artifact, not just its output file.
A deployment pipeline embeds production tokens in build logs. What is required?|Revoke exposed tokens and correct secret handling and logging|Delete the latest job title|Restrict model downloads|Reduce training batch size|Logs can leak active credentials; fix the exposure and invalidate compromised authorization material.
A canary model receives all privileged-user traffic first. What should rollout design reconsider?|Risk-based scope and consequences for the initial cohort|Whether the deployment is called canary|Whether users see a badge|The container tag's length|A staged rollout should limit impact and expose representative evidence; concentrating high-impact users can increase risk.
A rollback artifact is approved, but the schema has changed incompatibly. What should release planning require?|Tested rollback across model, application, and data compatibility|An older weight file|A longer maintenance notice|A second artifact signature|Rollback must restore a working compatible system; artifact availability alone does not prove recoverability.
A developer bypasses CI to upload weights directly. What should enforce the intended release path?|Deployment permissions restricted to approved controlled workflows|Written guidance|Model-output filtering|A changelog entry|A release process is ineffective if alternate write paths allow unapproved promotion.
@4.4|Guardrails and action constraints
An output filter blocks prohibited phrases but an agent can still transfer money. What is missing?|Action-level authorization and transaction constraints|A larger phrase list|Lower model temperature|A friendlier refusal message|Content filters do not reliably enforce downstream transaction authority or limits.
A tool schema permits arbitrary destinations for document export. What should be constrained?|Approved recipients, destinations, and data scope|The tool's display name|Response verbosity|The order of JSON fields|Validate the action parameters that determine exposure; well-formed input can still request unauthorized disclosure.
A model can retry a denied operation through a different tool. What should architecture enforce?|Consistent policy across equivalent action paths|Per-tool warning text|Rate limits on the first tool|A shorter retry delay|Policy must apply to the underlying resource and action, not just one interface that can be bypassed.
A workflow requires approval, but approval covers a draft that can change before execution. What should bind the gate?|The final action parameters and approved scope|The initial conversation topic|The model name|A general user greeting|Approval must authorize what actually executes; changed material parameters require renewed validation.
A sandbox blocks filesystem writes but allows unrestricted network sends. What should reviewers conclude?|Isolation is incomplete for exfiltration threats|All harmful behavior is prevented|The model is now anonymous|No further action controls are needed|Sandbox protection depends on permitted capabilities; blocking one channel leaves others available.
A load test uses only valid short prompts. What security testing is missing?|Boundary, malformed, oversized, and resource-intensive inputs|More screenshots of success|Model naming consistency|Keyboard shortcuts|Robustness needs testing beyond normal paths, including inputs stressing validation and resource controls.
A safety filter rejects necessary benign medical terms. What should the team do?|Evaluate false positives and adjust controls without abandoning safeguards|Disable every safety control|Ignore user impact indefinitely|Assume every rejection is correct|Guardrails should be evaluated for both harmful misses and unnecessary blocking within the approved use case.
A guardrail returns approve after a parsing error. What should be corrected?|Use explicit validated decisions and safe error handling|Improve error wording|Increase output tokens|Reduce monitoring|Malformed responses should not become approvals; decision parsing and error behavior are part of the security boundary.
A document includes hidden instructions to invoke an admin tool. Which control provides the strongest execution boundary?|The tool rejects unauthorized callers and actions|A prompt asking the document to be honest|A larger context window|A citation attached to the document|Independent tool authorization limits consequences even when the model follows malicious content.
An agent can invoke a dangerous tool repeatedly after approval of one action. What should approval controls specify?|Operation count, parameters, scope, and validity period|The conversation's first message|The tool vendor|Output language|Authorization should be bounded to the intended action rather than interpreted as unlimited future permission.
@4.5|Authentication and identity
A team shares one production token among all agents. What design is stronger?|Distinct attributable identities with scoped credentials|One more powerful shared token|A secret embedded in every prompt|Anonymous access behind an obscure URL|Distinct identities support least privilege, revocation, and attribution without broad shared authority.
An API accepts a user-supplied string saying administrator as identity proof. What should replace this?|Verified authentication with trusted claims|A longer claimed role name|Model-generated identity confirmation|A hidden HTML input|Identity assertions must be verified through a trusted authentication mechanism, not accepted from untrusted content.
A non-human agent needs ongoing API access. Which pattern is most appropriate?|Managed workload identity with narrowly scoped credentials|A shared human password|A reusable password in source code|A screenshot of an employee's MFA challenge|Workload authentication should support automation without borrowing broad human credentials or defeating lifecycle controls.
A federated login succeeds, but an application trusts any token issuer. What must be validated?|Trusted issuer, audience, signature, expiry, and relevant claims|That the token parses|That it contains an email field|That it is base64 encoded|A syntactically valid token is not necessarily authentic or intended for this application.
An agent forwards a user's token to an unrelated tool. What should be reviewed?|Audience restrictions and appropriate delegated authorization|Token string length|Tool documentation style|Model response quality|Tokens should be used only for authorized audiences and purposes; forwarding can expose credentials or enable misuse.
An agent stores long-lived credentials in conversation memory. What should change?|Use protected secret management outside model-visible memory|Summarize the credential|Translate the credential|Label the memory private|Conversation memory is not a secure secret store; limit exposure and use controlled credential delivery.
A user signs out, but a delegated agent session remains active indefinitely. What should design address?|Session lifetime, revocation, and delegated authority termination|A goodbye message|Model context size|Output formatting|Delegated access needs lifecycle rules so authority does not persist beyond intended sessions or approvals.
A critical administrator account uses password-only authentication. What should be considered?|Stronger authentication appropriate to privileged access|A longer model description|A rate limit on inference tokens|An AI warning banner|Administrative compromise affects the entire platform; apply appropriate strong authentication and privileged-access controls.
A tool rotates its credentials but old agents keep cached copies. What should the platform support?|Credential refresh and reliable revocation handling|Silent fallback to a shared admin password|Indefinite acceptance of cached secrets|Embedding replacements in user-visible chat|Rotation and revocation must propagate safely to clients without creating insecure fallback access.
An agent acts for multiple users through one service identity. What should authorization preserve?|The initiating user's context and the agent's limited authority|The service identity's broad permissions|The last user's chat text|The user's display name|Delegation should not let a broad service account override the specific user's resource permissions.
@4.6|Authorization
A retrieval tool has read access to every tenant because filtering happens in the prompt. What should change?|Enforce tenant-aware access in the retrieval service|Strengthen the prompt wording|Increase embedding dimensions|Remove citations|Model instructions cannot reliably substitute for resource-level tenant authorization.
An agent asks for temporary production access for one investigation. Which pattern fits least privilege?|Approved just-in-time access limited by task and duration|Permanent global administrator access|A shared credential copied from another team|Unlogged wildcard access|Temporary scoped authorization reduces standing privilege while preserving an accountable approval path.
A model's confidence score determines whether it may execute a privileged action. What should determine authorization instead?|Verified identity, policy, resource, and action constraints|The longest generated rationale|The vendor benchmark|The model's self-reported seniority|Prediction confidence describes model uncertainty, not an entitlement to access resources or perform actions.
A tool checks authorization only when a session begins. What else should be considered?|Per-request checks reflecting current permissions and action scope|The initial greeting|The model's startup timestamp|An annual role review|Permissions or targets can change during a session; critical operations need current authorization.
An employee changes departments but retains the assistant's old document access. What should happen?|Update entitlements and verify derived access paths|Update the email signature|Retrain the model|Clear public browser caches|Access should follow the current role across retrieval, caches, and delegated capabilities.
Two agents can each approve the other's payment requests. What should review examine?|Whether the workflow undermines separation of duties|Whether both models are accurate|Their total token budget|Their language settings|Mutual automated approval may defeat intended independent authorization and accountability.
An authorization rule uses data sensitivity, user clearance, and purpose. Which approach is most closely associated?|Attribute-based access control|Round-robin routing|Text summarization|Dataset compression|Attribute-based policies evaluate relevant subject, resource, action, and contextual attributes.
A tool accepts a user-approved read request but changes the HTTP method to delete. What must enforcement check?|The actual operation and resource at execution|The original chat intention|Whether a session exists|Whether the URL uses HTTPS|Authorization must cover the executed action; approval for reading cannot authorize deletion.
A parent agent delegates all its permissions to a child by default. What should improve?|Explicit bounded delegation with only necessary authority|Automatic privilege inheritance without review|A larger child context window|A shared unrestricted session|Delegation should preserve limits and accountability rather than expand authority across an agent chain.
A user manipulates a prompt to request another user's identifier. What should protect the target record?|Object-level authorization tied to the authenticated requester|Hiding identifiers in the UI|Limiting answer length|Asking users to be polite|Predictable or user-supplied identifiers must not bypass authorization to the underlying object.
@4.7|Identity lifecycle and audit

A new tool integration creates service accounts without owners. Access reviews examine employees but ignore autonomous services. An investigator sees tool calls but cannot link them to an initiating user. A session timeout closes the UI but leaves background actions running. A token accounting report shows one agent consuming most capacity. An identity inventory lists accounts but not their downstream tool permissions. An emergency access account was used during an incident. A terminated contractor's agent remains authorized through a separate service account. What should offboarding cover?|Delegated and dependent non-human access tied to the person|The contractor's laptop|The human SSO account|The email mailbox|Offboarding must trace authority beyond the human login to agents, tokens, and service dependencies.
A periodic review confirms role names but never tests actual permissions.
